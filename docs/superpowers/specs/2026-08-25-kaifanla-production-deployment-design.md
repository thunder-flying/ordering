# 「开饭啦」生产部署设计

日期：2026-08-25

## 1. 背景与目标

项目是个人菜单与选菜清单工具，由原生微信 TypeScript 小程序、Next.js 16 模块化单体、MySQL 8.4 和 Prisma 7 组成。服务端同时承载小程序 API、单管理员后台与图片访问。产品不包含下单、支付、门店、桌台、配送、退款或员工权限。

本次上线使用已备案域名 `guziyi.cn`、API 子域名 `api.guziyi.cn`、微信小程序 AppID `wx0006792d6129b164` 和专用阿里云 ECS。小程序名称统一为“开饭啦”。正式名称仍需在微信公众平台完成申请。

生产目标是：HTTPS 可访问、数据库不暴露公网、数据与图片可持久化、发布失败可回滚、备份可实际恢复，并能通过真实微信设备完成核心流程验收。

## 3. 总体架构

生产采用本机构建、服务器运行 Docker Compose 的方式。服务器不保存项目源码，也不承担 Next.js 生产构建。

```text
微信小程序 ─┐
            ├─ HTTPS → Nginx → Next.js 服务 → MySQL 8.4
管理后台 ───┘                    │
                                └→ 上传图片持久卷

备份任务 → MySQL 逻辑备份 + 图片 → 本地加密仓库 → 私有 OSS
```

容器职责如下：

- `nginx`：唯一公网入口，发布 80/443，完成 HTTPS、反向代理、请求体限制、安全响应头和频率限制。
- `server`：Next.js standalone 运行时，内部监听 3000，承载 `/api/v1`、`/admin` 和受控媒体路由。
- `mysql`：MySQL 8.4，内部监听 3306，只允许 `server` 与受控维护任务访问。
- `certbot`：只在签发或续期证书时运行，共享 ACME 与证书卷。
- `backup`：按计划执行数据库导出、Restic 加密快照、校验、保留策略与 OSS 同步。

Compose 使用内部网络连接应用与数据库。MySQL 和 Next.js 不映射宿主机端口。数据库、上传图片、证书、本地备份仓库分别使用独立持久卷或权限受控的宿主机目录。

## 4. 资源控制

服务器创建 2 GiB Swap 文件，权限为 `0600`，并设置较低的 `vm.swappiness=10`。Swap 只应对瞬时峰值，不作为真实内存扩容。

MySQL 使用面向小内存实例的配置，将 InnoDB 缓冲池控制在约 256 MiB；Next.js 通过 Node 内存参数限制堆上限；Nginx 保持少量 worker。容器配置明确的内存上限和日志轮转，避免单个服务耗尽系统资源。备份任务错峰运行，并设置最长执行时间，避免异常任务长期占用资源。

## 5. 镜像与运行时安全

Next.js 使用多阶段 Dockerfile 构建 standalone 镜像。构建阶段执行冻结依赖安装、Prisma Client 生成、Next.js 构建和上传清理 CLI 编译；运行镜像只包含运行所需产物、Prisma 迁移和清理命令。

`server` 使用固定的非 root UID 运行，根文件系统只读，仅 `/tmp` 与上传目录可写。Nginx 关闭版本暴露并限制可写目录。基础镜像在实施时固定到明确版本和镜像摘要，避免部署过程无意漂移。

生产镜像以 UTC 时间戳和内容摘要识别，不依赖 Git 提交信息。构建完成后在本地保存镜像摘要，通过加密 SSH 通道上传并在服务器加载。

## 6. 域名、TLS 与边缘策略

`api.guziyi.cn` 创建 A 记录并指向 `8.137.174.33`。DNS 生效后使用 HTTP-01 验证签发证书，HTTP 除 ACME challenge 外全部跳转到 HTTPS。证书续期由定时任务执行，续期成功后平滑重载 Nginx。

同一域名承载：

- 小程序 API：`https://api.guziyi.cn/api/v1/*`
- 管理后台：`https://api.guziyi.cn/admin/login`
- 菜品与头像媒体：`https://api.guziyi.cn/media/*`
- 健康检查：`https://api.guziyi.cn/api/v1/health`

Nginx 设置 TLS 1.2/1.3、安全响应头、合理的代理超时与请求体上限。管理员登录、微信认证和普通 API 使用不同的限流区域；管理页面和私有头像禁止缓存，带内容哈希的公开菜品图片允许长期缓存。所有代理请求保留 Host、HTTPS 协议与请求 ID。

## 7. 服务器与网络安全

阿里云安全组和主机防火墙只允许 80/443 公网访问。SSH 22 仅允许可信公网来源；若当前网络地址会变化，先保留可恢复入口，再逐步收紧。

专用密钥连续验证成功后禁用 SSH 密码认证。任何 SSH 配置变更都先执行配置校验并保持当前会话开启，再用第二个连接验证，避免锁死服务器。

生产环境文件存放在服务器权限受控目录，属主为 root，权限为 `0600`。项目文件、容器镜像、日志、备份清单和聊天记录都不包含明文凭据。

## 8. 密钥与生产环境配置

仅微信 AppSecret 和已配置的管理员密码哈希需要从现有本地受限环境安全传入。生产数据库密码、OpenID HMAC 密钥、用户会话 pepper、管理员会话密钥和 Restic 仓库密码在服务器上分别随机生成，彼此不复用。

生产环境至少包含：

- `DATABASE_URL`
- `OPENID_HMAC_SECRET`
- `WECHAT_APP_ID`
- `WECHAT_APP_SECRET`
- `USER_SESSION_PEPPER`
- `ADMIN_USERNAME`
- `ADMIN_PASSWORD_HASH`
- `ADMIN_SESSION_SECRET`
- `UPLOAD_ROOT`

OSS 使用专用 RAM 身份，权限只覆盖指定私有 Bucket 和应用备份前缀，不使用阿里云主账号密钥。访问凭据只保存在服务器受限环境中。所有诊断命令只输出“是否配置”和长度校验结果，不输出实际值。

## 9. 数据库、迁移与初始数据

MySQL 数据目录使用独立持久卷。数据库账号使用随机强密码，应用账号只获得业务数据库所需权限。3306 不映射到宿主机或公网。

首次部署顺序为：启动 MySQL并等待健康、执行 `prisma migrate deploy`、按明确选择执行幂等种子、启动 Next.js、通过内部和外部健康检查后开放流量。

后续发布在变更服务前先完成备份。数据库迁移必须向前兼容当前应用镜像；自动回滚只回滚应用镜像，不自动逆向迁移或删除数据。任何破坏性 Schema 变更需要单独设计、双阶段发布和人工确认。

## 10. 上传文件与持久化

`UPLOAD_ROOT` 指向专用持久卷。菜品图片和头像继续通过现有服务端签名检查、原子写入和访问控制实现，不把头像目录直接暴露为 Nginx 静态目录。

容器重建、服务器服务重启和应用镜像回滚不得改变上传卷。每日维护任务运行已编译的 `cleanup-uploads` 命令，只清理数据库明确标记且不再引用的文件，并限制最长执行时间。

## 11. 备份与恢复

采用服务器本地加密仓库与阿里云 OSS 双重备份。OSS Bucket 位于 `cn-chengdu`，保持私有，启用服务端加密、版本保护和生命周期规则。

每日凌晨执行以下流程：

1. 使用一致性参数导出 MySQL，写入临时文件并校验压缩数据。
2. 将数据库导出与上传图片写入 Restic 加密快照。
3. 校验仓库结构和最新快照。
4. 保留最近 7 个日快照和 4 个周快照。
5. 将加密仓库同步至 OSS 私有前缀。
6. 写入不含凭据的成功时间、快照 ID 和校验结果。

恢复脚本必须要求指定快照、新数据库名和空的媒体目录；拒绝覆盖生产数据库、生产上传目录、根目录或符号链接目标。上线前从 OSS 副本恢复到独立数据库和独立目录，比较关键表行数、清单快照值和图片 SHA-256。恢复验证通过后才视为备份能力可用。

## 12. 发布与回滚

本地发布门禁通过后构建生产镜像，记录镜像摘要并经 SSH 上传。服务器部署脚本先校验 Compose 展开结果和必需环境变量，再执行备份、迁移、容器更新与外部 HTTPS 健康检查。

更新前保存当前应用镜像摘要。新镜像健康检查失败时，保留日志并只恢复旧的 `server` 镜像；MySQL、上传卷、证书和备份卷不重建、不清空。首次部署没有旧镜像时，失败状态保持服务不开放，并保留可诊断日志。

所有脚本使用拒绝式默认值：缺少域名、镜像、数据库密码或密钥时立即失败；不会用测试密码、示例域名或空值继续。

## 13. 监控与运维

每五分钟检查 HTTPS 健康、容器健康、根分区与数据目录使用率、内存与 Swap、证书剩余天数、最近备份时间和 systemd 失败单元。磁盘使用率达到 80%、证书剩余少于 21 天、备份超过 30 小时或健康检查失败时返回非零状态并写入系统日志。

Docker 日志设置大小和数量上限；Nginx 与维护日志按日轮转并保留 14 天。日志只包含时间、级别、请求 ID、路径、状态码和安全白名单字段，不记录请求正文、令牌、AppSecret、数据库地址或密码。

阿里云云监控负责主机 CPU、内存、磁盘和服务失败告警。第三方通知凭据不写入仓库。

## 15. 验证与完成标准

代码门禁包括服务端契约测试、Lint、类型检查、单元测试、MySQL 集成测试、生产构建，以及小程序测试和类型检查。生产配置另有 Compose、Nginx、密钥缺失、端口暴露、只读文件系统、备份恢复和部署失败回滚测试。

服务器验收包括：

- HTTPS 健康接口返回 200，证书域名与有效期正确。
- 管理后台可登录，登录与 API 限流有效。
- 宿主机和公网无法连接 MySQL 3306。
- 容器重建后数据库和图片仍存在。
- 最新备份能从 OSS 恢复到独立目标并通过数据与文件校验。
- 健康、证书、磁盘、备份和清理定时任务实际运行。

小程序使用两个微信账号在 iOS 和 Android 真机验证登录、资料设置或跳过、菜单、搜索、收藏隔离、草稿、保存清单、编辑、复制、删除、清空数据、账号注销、图片与头像。体验版通过后提交审核，审核通过后发布，并用无关微信账号确认可搜索和访问。

## 16. 外部操作边界

以下操作必须使用资源所有者的阿里云或微信公众平台身份完成：

- 创建 DNS A 记录。
- 创建成都地域的私有 OSS Bucket、RAM 身份与最小权限策略。
- 在阿里云安全组限制端口来源并配置云监控告警。
- 在微信公众平台申请“开饭啦”正式名称、配置合法域名、完善隐私声明、上传体验版、提交审核和发布。

密钥和密码不通过聊天发送。若控制台步骤无法由自动化工具代办，部署过程提供逐步操作说明，并在每一步后用 DNS、HTTPS、OSS 或微信真机行为验证实际结果。

## 17. 项目协作约束

整个实施过程不执行任何 Git 命令。尤其不会执行 `git add`、`git commit` 或等价操作。文件修改使用补丁方式完成，只触及本设计和后续实施计划明确列出的生产部署、名称、API 域名、验证与运维文件。
