# 个人选菜清单小程序设计规格

日期：2026-08-19  
状态：已完成对话设计，等待用户审阅书面规格  
项目性质：个人主体、非商业、正式发布、长期运行

## 1. 背景与目标

本项目最初设想为点菜小程序。由于微信小程序主体为个人，正式发布版本收缩为“个人选菜清单工具”，避免形成餐饮交易和商家履约闭环。

系统向所有微信用户开放。用户浏览同一份由管理员维护的公共菜单，各自保存私有收藏和选菜清单。菜单可以展示参考价格并计算预估合计，但不会产生订单，也不会把清单发送给商家。

核心目标：

- 使用原生微信小程序提供自然、稳定的移动端体验。
- 使用 React + Next.js 同时承载管理后台和全部服务端 API。
- 支持多名微信用户，收藏、草稿、清单和个人资料严格隔离。
- 支持个人主体正式发布所需的备案、隐私说明和长期运维能力。
- 使用自购中国内地服务器、自有域名、HTTPS 和 MySQL 长期部署。
- 在低维护成本下保证数据可备份、服务可恢复、版本可升级。

成功标准：新用户能够完成静默登录、可选资料完善、选菜、收藏和保存清单；管理员能够维护公共菜单；任何用户都无法访问其他用户的私有数据；容器重启、版本升级或单机故障后能够依靠持久化数据和备份恢复。

## 2. 明确不做的功能

首版及当前产品定位均不包含：

- 微信支付或任何支付方式。
- 下单、订单、接单、制作、配送、取餐、完成等履约流程。
- 堂食、到店自取、桌号、取餐码、桌台管理和桌码生成。
- 退款、售后、发票、优惠券、积分、会员等级和营销活动。
- 多门店、多商户、库存、规格 SKU、固定口味选项和加料。
- 员工账号、角色权限和多管理员体系。
- 用户之间的分享、公开清单或协同编辑。
- 用户自建菜品。
- 管理员查看用户列表、收藏明细或个人清单内容。

界面文案统一使用“选择”“当前清单”“保存清单”“参考价格”“预估合计”，不使用“购物车”“下单”“结算”“订单”“接单”等交易性词语。

## 3. 开源项目调研与取舍

本项目不直接复刻现有餐饮系统。调研对象用于理解常见的信息架构、菜单交互和后台 CRUD，再按个人主体和 Next.js 约束重新设计。

| 项目 | 主要功能 | 架构与技术栈 | 优点 | 不适合本项目的部分 |
| --- | --- | --- | --- | --- |
| [yshop-drink](https://github.com/guchengwuyue/yshop-drink) | 扫码点餐、外卖、自取、多门店、SaaS、订单、支付、优惠券、打印 | Java 17、Spring Boot 3、Spring Security、MyBatis Plus、Redis、Vue 3、uni-app | 餐饮功能完整，后台与移动端模块清晰 | 交易、多租户和营销功能远超需求；不是 Next.js；部署组件较多 |
| [siam-server](https://github.com/siam1026/siam-server) | 多门店、用户端、商家端、配送端、库存、会员、统计、打印 | Spring Boot、MyBatis Plus、Redis、RocketMQ、WebSocket、Vue、uni-app | 展示了大型餐饮系统的领域拆分和运营后台 | 体系庞大，包含配送、库存、营销和多角色；维护成本过高 |
| [sky-take-out](https://github.com/Sonder-MX/sky-take-out) | 菜品、套餐、订单、微信登录、商家管理和外卖业务 | Spring Boot、MyBatis、MySQL、Redis、Vue、uni-app、REST API | 教学结构直观，菜单与管理端 CRUD 容易理解 | 以交易和订单为中心；Java 技术栈与目标不一致；仍需移除大量业务 |
| [bee](https://github.com/woniudiancang/bee) | 原生小程序餐饮商城、点餐、外卖、排队、支付、配送 | 原生微信小程序前端，后端依赖第三方 API 平台 | 原生小程序页面和交互有参考价值，启动门槛低 | 后端不由项目完整自持；交易功能过多；不满足 Next.js 自建后端要求 |
| [litemall](https://github.com/linlinjava/litemall) | 商品、分类、搜索、收藏、购物车、订单、管理后台和统计 | Spring Boot、Vue、原生微信小程序、MySQL | 模块完整、文档较多，原生小程序与后台分层值得参考 | 属于完整电商系统；技术栈和业务范围都明显过重 |

调研结论：

- 保留成熟项目中“分类—菜品—收藏—临时选择—历史记录”的信息结构。
- 保留管理端对分类、菜品、图片、排序和上下架的 CRUD 思路。
- 不引入订单状态机、支付、库存、门店、营销、Redis、消息队列或微服务。
- 不基于上述项目二次开发，因为删除不需要的业务并改写为 Next.js 的成本高于按明确边界新建模块化单体。

## 4. 技术方案比较与决策

曾考虑三种方案：

1. 一个模块化 Next.js 应用 + MySQL：管理后台和 API 一起构建部署，维护成本最低，内部仍按业务模块隔离。
2. 管理后台和 API 拆成两个 Next.js 应用：部署隔离更强，但要维护两套构建、配置和容器，当前规模没有对应收益。
3. Next.js + SQLite：初始化简单，但公开长期运行时的并发写入、备份恢复和后续迁移不如 MySQL。

最终采用方案 1。这里的“单体”只表示管理后台与 API 是一个可部署的 Next.js 服务，不表示代码混在一起。原生微信小程序仍是独立客户端。

## 5. 总体架构

代码仓库采用工作区结构：

```text
ordering/
├─ apps/
│  ├─ miniapp/          原生微信小程序（WXML、WXSS、TypeScript）
│  └─ server/           Next.js 管理后台、API 和业务模块
├─ packages/
│  └─ contracts/        无运行时依赖的 API 类型、错误码和共享常量
├─ deploy/              Docker Compose、Nginx 和部署配置
└─ docs/                设计、计划和运维文档
```

运行关系：

```text
原生微信小程序
        │ HTTPS / JSON
        ▼
Nginx ───────────────► 菜品图片
        │
        ▼
Next.js 模块化单体
├─ React 管理后台
├─ 小程序 API
├─ 管理 API
├─ 身份与会话
└─ 领域模块
        │ Prisma
        ▼
      MySQL
```

Next.js 使用 App Router。页面层、Route Handlers、服务层和数据访问层分离，业务模块至少包含：身份、个人资料、分类、菜品、收藏、清单、上传文件、统计和管理员会话。

生产环境使用一个域名：

- `https://menu.example.com/admin`：管理后台。
- `https://menu.example.com/api/v1/*`：小程序和后台 API。
- `https://menu.example.com/media/dishes/*`：公开菜品图片。

实际域名在购买并备案后替换。小程序只需配置一个 HTTPS 服务器域名。

## 6. 微信小程序功能

### 6.1 首次进入与个人资料

首次启动时，小程序先调用 `wx.login` 完成静默身份建立，然后立即展示资料完善页。用户可以通过 `open-type="chooseAvatar"` 主动选择头像，通过 `input type="nickname"` 选择微信昵称或手动填写，也可以点击“暂时跳过”。

跳过不会限制任何基本功能。系统使用默认头像和“微信用户”作为初始资料。用户之后可以在“我的”页面修改资料。

旧式 `wx.getUserProfile` 不作为真实头像昵称来源。头像昵称属于非必要个人信息，必须由用户主动操作提供。

### 6.2 主要入口

小程序包含四个主要入口：

1. **选菜**：分类导航、菜品列表、关键词搜索、图片、名称、简介、参考价格和收藏操作。
2. **当前清单**：调整数量，为每道菜填写一条自由备注，查看预估合计，填写清单名称后保存。
3. **我的清单**：查看本人保存的清单，支持打开、编辑、复制和删除。
4. **我的**：头像昵称、收藏入口、隐私说明、清空个人数据和注销账号。

每道菜只有数量和自由备注，不支持结构化口味、大小份、加料或 SKU。当前未保存清单保存在小程序本地；收藏和已保存清单保存在服务端，可在不同设备登录同一微信身份后恢复。

### 6.3 清单规则

- 用户从公共菜单选择菜品并保存为带名称的个人清单。
- 清单完全私有，不分享、不公开、不协同。
- 数量必须是 1–99 的整数。
- 每个条目只有一条自由备注，最多 100 个 Unicode 字符。
- 客户端显示预估合计，但服务端按当前数据库价格重新计算。
- 保存时记录菜品名称、参考价格和必要展示字段的快照。
- 修改菜品价格不改变历史清单。
- 已下架菜品可以在旧清单中显示，但不能加入或保存到新清单；编辑包含下架菜品的旧清单时，必须先移除该菜品。
- 编辑并重新保存旧清单时，按保存时的当前价格重建快照和预估合计。
- 复制旧清单时只复制仍然上架的菜品，使用当前价格，并明确提示被跳过的项目。

## 7. Next.js 管理后台

管理后台只面向一个管理员，不建设员工、角色或权限体系。

功能范围：

- 管理员登录和退出。
- 匿名数据概览：用户总数、近 7 日活跃用户数、收藏总数、清单总数和热门菜品聚合。
- 分类新增、编辑、排序、启用、停用和软删除。
- 菜品新增、编辑、分类调整、图片、简介、参考价格、排序、上架、下架和软删除。
- 图片上传、替换和未引用文件的安全清理。

停用分类会使其下全部菜品从用户菜单中消失。分类仍有关联菜品时禁止删除，管理员必须先移动或软删除这些菜品。替换图片后，旧文件进入 7 天待清理期；只有确认没有菜品、用户头像或历史展示引用时才能物理删除。

后台不提供用户列表，不展示头像、昵称、`openid`、个人收藏或清单内容。聚合统计只返回计数和菜品维度数据。

管理员账号名和密码哈希来自生产环境变量。成功登录后使用最长 12 小时、带 `Secure`、`HttpOnly` 和 `SameSite=Strict` 属性的 Cookie 建立后台会话。修改请求同时校验来源和 CSRF 防护信息。连续失败登录触发限流。

## 8. 数据模型

数据模型使用内部不可枚举 ID。核心表如下：

### 8.1 用户与会话

- `users`：内部 ID、`openid` 的 HMAC 摘要、昵称、头像文件引用、首次登录时间和最近登录时间。
- `user_sessions`：用户 ID、随机会话令牌哈希、到期时间、最后使用时间、创建信息。

数据库不保存明文 `openid`。服务端用独立密钥计算确定性的 HMAC 摘要以完成用户匹配，密钥只存在生产环境变量中。会话令牌只向客户端返回一次，数据库只存哈希；会话最长有效期为 30 天，过期后重新执行静默登录。

### 8.2 菜单

- `categories`：名称、排序、启用状态、软删除时间和审计时间。
- `dishes`：分类 ID、名称、图片文件引用、简介、参考价格分值、排序、上架状态、软删除时间和审计时间。

参考价格使用“分”为单位的整数存储，禁止使用浮点数计算金额。

### 8.3 用户私有数据

- `favorites`：用户 ID、菜品 ID、创建时间；用户与菜品组成唯一约束。
- `lists`：用户 ID、名称、预估合计快照、幂等请求 ID、创建和更新时间。
- `list_items`：清单 ID、可空菜品 ID、菜品名称快照、参考价格快照、数量、备注和排序。

所有收藏和清单查询都使用服务端会话解析得到的用户 ID 作为条件，接口不接受客户端指定数据所属用户。

### 8.4 文件

- `uploads`：文件 ID、所有者类型、用途、存储路径、原始类型、检测类型、大小、哈希、引用状态和创建时间。

菜品图片公开读取。用户头像使用不可猜测的文件标识和 10 分钟有效的签名 URL，不开放目录浏览；头像只能由所属用户取得有效访问地址。注销账号时删除头像文件。

## 9. 登录、会话与数据流

微信登录流程：

```text
wx.login 获取临时 code
→ POST /api/v1/auth/wechat
→ Next.js 使用 AppID/AppSecret 调用微信 code2Session
→ 计算 openid HMAC 并创建或更新用户
→ 生成随机会话令牌
→ 小程序安全存储令牌并在 API 请求中携带
```

AppSecret 永远不会下发到小程序。用户会话失效时，客户端重新执行静默登录并最多重试一次原读取请求。

选菜保存流程：

```text
获取分类和已上架菜品
→ 用户在本地建立当前清单
→ 提交名称、菜品 ID、数量、备注和唯一请求 ID
→ 服务端验证会话、输入和菜品状态
→ 服务端读取参考价格并计算合计
→ 在一个数据库事务中写入清单和快照条目
→ 返回已保存清单
```

网络重试使用唯一请求 ID 保证幂等，同一用户用同一请求 ID 不会创建重复清单。

## 10. API 边界

API 统一使用 `/api/v1` 前缀，并采用一致的成功响应、错误码、中文安全提示和请求 ID。请求与响应类型放在 `packages/contracts`，小程序客户端和 Next.js 服务端从同一契约构建，避免字段定义漂移。

小程序 API 分组：

- 身份：微信静默登录、退出当前会话。
- 个人资料：读取、修改昵称、上传头像、清空数据、注销。
- 菜单：读取启用分类、已上架菜品、搜索和菜品详情。
- 收藏：读取、添加和取消。
- 清单：列表、详情、创建、编辑、复制和删除。

管理 API 分组：

- 管理员会话：登录、登出和当前会话。
- 数据概览：匿名聚合统计。
- 分类：CRUD、排序和状态变更。
- 菜品：CRUD、排序和状态变更。
- 上传：图片上传、替换和安全清理。

服务端使用统一校验层，首版边界固定为：分类名称 1–20 个字符、菜品名称 1–40 个字符、菜品简介最多 300 个字符、清单名称 1–40 个字符、条目数量 1–99、条目备注最多 100 个字符、参考价格 0–9,999,999 分。菜品图片接受 JPEG、PNG、WebP 且不超过 5 MB；头像接受 JPEG、PNG、WebP 且不超过 2 MB。管理端与小程序端使用不同会话机制，互不通用。

## 11. 异常处理与用户体验

- 菜品加载失败时保留页面骨架并提供重新加载按钮。
- 保存时断网不清空本地草稿，恢复网络后允许再次保存。
- 会话失效时自动静默登录并重试一次；仍失败则提示稍后重试。
- 菜品下架时在当前清单中标记，阻止保存并提示移除。
- 图片加载失败时显示本地默认占位图。
- 重复保存请求返回第一次成功创建的清单，不生成副本。
- 管理员编辑时比较记录更新时间，发现冲突则要求刷新，避免静默覆盖新数据。
- 服务端异常返回请求 ID，不向客户端泄露堆栈、SQL、环境变量或内部路径。
- 日志采用结构化格式，并对会话令牌、密码、AppSecret、`openid` 和个人资料脱敏或完全排除。

## 12. 隐私、安全与防滥用

- 头像昵称为可选信息，首次进入优先引导但允许跳过。
- 提供隐私说明、清空个人数据和注销账号入口。
- “清空个人数据”只删除收藏和清单，保留当前登录身份、头像和昵称；操作前要求二次确认。
- 注销在一个事务中作废并删除全部用户会话，删除昵称、头像、收藏、清单、用户行和 `openid` HMAC 映射；只保留无法关联个人身份的聚合统计。相同微信用户再次进入时会获得新的内部用户 ID，视为全新账号。
- 所有私有资源访问都执行对象所有权检查，防止通过修改 ID 越权访问。
- 公共接口、登录、保存和上传分别配置频率限制。
- 上传文件同时校验扩展名、MIME 声明、实际文件类型和大小，使用服务端生成的文件名。
- Nginx 设置请求体上限、安全响应头和合理超时。
- 管理后台启用 CSRF 防护、登录失败限流、会话到期和关键操作审计日志。
- MySQL 不监听公网地址；公网只开放 HTTPS 和受限运维入口。
- SSH 使用密钥登录，并通过安全组限制来源；禁止密码直登生产服务器。

## 13. 部署与正式发布

### 13.1 生产拓扑

生产环境建议从 2 核 CPU、4 GB 内存和 40–80 GB SSD 的中国内地云服务器起步。Docker Compose 运行：

- `nginx`：TLS 终止、反向代理、静态菜品图片、限流和安全头。
- `server`：唯一 Next.js 服务。
- `mysql`：唯一主数据库，只在内部容器网络开放。

MySQL 数据、公开菜品图片和私有头像分别挂载到明确的持久化卷，不能写入容器临时层。

### 13.2 域名与备案

发布步骤：

1. 注册并实名认证自有域名。
2. 购买中国内地云服务器。
3. 通过接入云厂商完成域名 ICP 备案。
4. 在微信公众平台完成小程序备案。
5. 配置有效 HTTPS 证书和自动续期。
6. 在微信后台配置服务器域名、隐私保护指引和服务类目。
7. 在小程序显著位置按要求展示备案编号。
8. 使用体验版、真机和正式域名验收后提交审核。

工信部将小程序纳入移动互联网应用程序备案范围，正式发布时以当时微信公众平台和接入服务商的实际材料清单为准：

- [工业和信息化部关于开展移动互联网应用程序备案工作的通知](https://www.miit.gov.cn/zwgk/zcwj/wjfb/tz/art/2023/art_920db564162e4312916a01bed6540ad8.html)
- [微信小程序服务类目与资质要求](https://developers.weixin.qq.com/miniprogram/product/material/)

产品提交审核时必须与“个人选菜清单工具”的真实功能和文案一致，不通过隐藏功能或选择不匹配类目的方式规避审核。最终是否通过由提交时的服务类目、内容和审核规则决定。

## 14. 备份、监控与升级

- MySQL 每日自动备份，保留最近 7 份日备份和最近 4 份周备份。
- 上传文件每日增量备份。
- 数据库和文件至少保留一份服务器外副本；首版可使用云对象存储作为备份目标，之后也可迁移为正式图片存储。
- 每月执行一次抽样恢复测试，确认备份不是仅生成但不可恢复。
- 提供不泄露内部信息的 `/health` 健康检查。
- 监控 Next.js 和 MySQL 健康状态、HTTP 错误率、磁盘容量、备份结果和证书到期时间。
- Next.js、Node.js、MySQL 和基础镜像使用固定版本；生产环境不自动升级。
- 升级前先备份，数据库迁移先在测试环境验证，并准备应用镜像和数据库迁移的回滚步骤。

## 15. 测试策略

### 15.1 单元测试

- 参考价格整数计算和预估合计。
- 数量、名称、备注和价格边界。
- 上下架、历史快照和复制过滤规则。
- 会话、所有权和权限判断。
- 文件类型与大小校验。

### 15.2 API 集成测试

- 模拟微信 `code2Session`，验证新建用户、重复登录和会话失效。
- 收藏和清单完整增删改查。
- 用户 A 无法读取、修改或删除用户 B 的数据。
- 客户端伪造价格不会影响服务端合计。
- 重复请求 ID 不会生成重复清单。
- 注销后资料、会话、收藏和清单均不可恢复。
- 分类和菜品状态变更对用户查询的影响。

### 15.3 管理后台端到端测试

- 管理员登录、失败限流和退出。
- 分类与菜品 CRUD、排序、上下架和图片替换。
- 并发编辑冲突提示。
- 统计页面只展示聚合数据。
- 普通用户令牌不能调用管理接口。

### 15.4 小程序测试

- 微信开发者工具中的页面、组件和 API 客户端测试。
- 真机检查首次资料页、跳过、重新完善、搜索、收藏和清单。
- 断网、弱网、会话过期、图片失败和服务端错误场景。
- 不同微信账号之间的数据隔离。
- 正式备案域名和 HTTPS 证书兼容性。

### 15.5 部署验收

- 重启任意容器后数据库和图片不丢失。
- MySQL 端口无法从公网连接。
- 从独立备份恢复到临时环境后关键记录和文件可用。
- 健康检查、错误告警、磁盘告警和备份失败告警能够触发。

## 16. 分阶段实施

实施分成三个可独立验收的阶段，但共享本设计与同一代码仓库：

1. **基础设施与 Next.js 后台/API**：工作区、数据库、身份、菜单、上传、收藏、清单、管理后台和自动化测试。
2. **原生微信小程序**：登录、资料、菜单、搜索、收藏、当前清单、历史清单、个人数据管理和真机测试。
3. **部署备案与发布**：Docker Compose、Nginx、HTTPS、备份监控、域名备案、小程序备案、隐私配置和正式审核。

任何阶段都不增加本规格明确排除的交易、履约或多角色功能。新增范围必须重新设计并获得确认。

## 17. 首版验收标准

首版必须同时满足：

1. 新用户可通过 `wx.login` 静默建立身份，首次优先看到头像昵称引导，也能跳过。
2. 所有用户浏览同一份公共菜单，收藏和清单按用户严格隔离。
3. 当前清单支持数量、单条自由备注、参考合计、命名保存，并在断网时保留本地草稿。
4. 已保存清单支持查看、编辑、复制和删除。
5. 修改菜品价格不改变旧清单；下架菜品不能进入新清单。
6. 管理员能维护分类、菜品、图片、排序和上下架，只能查看匿名聚合统计。
7. 用户能清空个人数据和注销账号，注销后相关会话及个人数据被删除。
8. API 对伪造价格、重复保存、越权 ID、恶意上传和登录暴力尝试具有对应防护。
9. 容器重启不丢数据，数据库和文件能从服务器外备份恢复。
10. 小程序使用已备案域名和 HTTPS 真机运行，完成隐私配置、小程序备案并通过微信审核后正式发布。
